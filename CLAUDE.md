# meu-bot

- O `meu-bot` e o `meu-bot-admin-gestao` instalados em `~/Applications` são sempre o `origin/main` de agora: o hook `Stop` `scripts/hooks/rebuild-auto.sh` os reempacota (de um worktree fixo, `../meu-bot-build-main`) quando o `main` do GitHub muda. Mudança num branch ganha só `npm test` pelo hook; para vê-la na tela antes do merge, empacote à mão (`npm run dist…` de dentro do worktree, skill `rebuildar`) e lembre que o próximo merge no `main` reinstala por cima.
- Release é automática depois do merge: o agente do launchd `scripts/release-auto.mjs` (instale com `node scripts/release-auto.mjs --instalar`) solta o staging 10 min depois do último merge e promove para estável 24 h depois, se o `meu-bot-staging` deste Mac (vindo da release, não de build local) confirmou a versão. Os dois staging instalados se atualizam pelo atualizador; não os empacote à mão. Componente da máquina que muda sobe a versão no próprio PR (o CI recusa sem), e mudança visível escreve seu item num arquivo próprio, `docs/changelog/<branch>.md` (veja o README da pasta), nunca direto no topo do `docs/CHANGELOG.md`: lá toda PR mexe nas mesmas linhas e dá conflito.
- Mudança que vai virar PR nasce num worktree próprio (`git worktree add -b <branch> ../meu-bot-<nome> origin/main`), nunca trocando de branch neste checkout: outras sessões (Claude, Cursor) usam este diretório ao mesmo tempo. A skill `contribuir` diz como preparar o worktree para empacotar.
- Antes de conferir uma mudança na tela, confirme que o app instalado é o seu build: `grep -a -c <símbolo novo> ~/Applications/<app>.app/Contents/Resources/app.asar`. O hook de rebuild de outra sessão pode ter reinstalado a partir de outro branch.
- Trabalho commitado num branch sem PR: o hook `Stop` `scripts/hooks/pr-lembrete.sh` avisa ao fim da resposta; se o branch é seu, abra a PR pela skill `contribuir` sem esperar o usuário pedir.
- Nenhuma pessoa é gargalo (decisão do usuário em 15 nov 2026): PR sua entra sozinha: o workflow `auto-merge.yml` liga o auto-merge quando a Revisão Claude termina, e o `main` exige o check `testes` e as conversas da revisão resolvidas. O seu trabalho é provar a mudança, corrigir o que a revisão apontar e **resolver** cada conversa (skill `contribuir`); PR que não deve entrar fica em rascunho ou ganha o rótulo `nao-mesclar`; o staging do site acompanha a main pelo agente da release (`scripts/site-publicar.mjs --so-staging`) e é sempre a main: ramo não vai para o staging (o script recusa o que não é o `origin/main`; para ver um ramo antes do merge, o Worker roda local, skill `publicar-site`); a chave da release sai do Chaveiro sem janela. Continua sendo do usuário: antecipar a estável antes das 24 h ("aprovado"), aprovar a produção do site (main → staging → produção: ela só recebe o commit que está no staging e que ele aprovou, `--aprovar <sha>` e depois `--producao`; skill `publicar-site`) e o que só ele pode fazer (contas externas, decisões de produto, testes na mão).
- Pendências e PRs em andamento vivem no Project #6 "meu-bot" do GitHub (skill `quadro`): leia o quadro no começo da sessão, mova os cartões você mesmo e nunca abra issue para pendência de acompanhamento (issue acorda o Claude automático; pendência é cartão rascunho).
